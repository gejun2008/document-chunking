Document Studio · Document Chunking

文档切分方案评测

把三个可上生产的候选方案都实现出来，在三个公开基准上用同一套 embedding、同一套指标跑了一遍，回答两个问题：自研的效果有没有短板，以及该选哪个方案。

结论

  1. 方案 1（自研）和方案 3（LangChain + 自研）都可以选，chonkie 不推荐。1 和 3 的效果差距在统计噪声范围内，选哪个主要看团队情况：想少引入依赖（10 个对 34 个）、自己掌控升级，选 1；langchain-core 已在白名单、团队本来就用 LangChain，选 3。
  2. 默认用 layout_aware，chunk_size 建议 200–300，可以按文档类型调整。有标题的文档上它比 fixed_size 好，没有标题时两者持平。semantic 更慢，效果也没有更好，一般不需要。
  3. 保留父子块结构，父块摘要不建议默认开启。父子块不需要 LLM，命中子块后可以把父块交给 LLM 做抽取，自研版本的答案完整率也远高于旧版。以前的父块摘要在 6 组测试里全部降低了召回（−1 到 −13 个点）；"每个 chunk 一句上下文"的做法表现更好（−0.3 到 +5.2），可以作为可选项，用公司的 LLM 复核后再决定。
实现方式

每种策略在三个方案里怎么实现

chunk 大小统一按 tiktoken（cl100k_base）计数，所有方案输出的 chunk 都保留原文和在文档中的精确位置。

策略自研chonkieLangChain + 自研
fixed_size
不需要外部服务		 递归切分：先按段落，过长再依次按行、句子（中英文标点）、词、token 切，然后合并到 chunk_size；overlap 按整句保留 SentenceChunker：按句子打包到 chunk_size，带 overlap；分隔符补充了中文标点 RecursiveCharacterTextSplitter（tiktoken 计数），分隔符补充了中文标点；库返回的位置在有 overlap 时不准，由我们重新定位
layout_aware
不需要外部服务		 用 markdown-it-py 解析 Markdown 语法树，按 1–3 级标题切章节；很短的章节合并；表格和代码块保持完整；超长章节回退到递归切分；标题路径加在 embedding 文本前 MarkdownChef 拆出表格和代码块并保持完整，其余文本用 RecursiveChunker 加 Markdown 规则切分（官方规则运行时要联网下载，已内置） MarkdownHeaderTextSplitter 按 #/##/### 标题切，超长章节再用 RecursiveCharacterTextSplitter；标题路径加在 embedding 文本前；库会改写换行和空白，位置由我们重新定位
semantic
需要 embedding		 正则切句（中英文），每句连同前后各一句一起做 embedding；相邻两句的距离超过全文第 90 百分位时切开；过小的块合并，过大的块再切 SemanticChunker，通过适配器接入同一个 embedding 服务；相似度阈值校准为 0.15，使平均 chunk 大小与自研相近 没有可用的现成实现（langchain_experimental 不建议用）；把自研算法封装成 LangChain 的 TextSplitter，可以直接接收 LangChain 的 Embeddings
context_enriched
需要 LLM		 在 fixed_size 外面包一层：取以 chunk 为中心约 1,500 token 的原文（文档较短时用全文）和 chunk 本身，让 LLM 写一句上下文，拼在 embedding 文本前；chunk 原文不变 库里没有这个功能，用自研的同一层包装 chonkie 的 fixed_size 库里没有这个功能，把自研的同一层封装成 LangChain 的 BaseDocumentTransformer

另外还实现了以前设计的"父子块 + 父块摘要"（ParentChildChunker）：先切约 1,024 token 的父块，可选地为每个父块调用一次 LLM 生成 1–2 句摘要（prompt 与旧版相同），再在父块内切 256 token 的子块，embedding 文本为 Context summary: {摘要} 加子块原文。每个块带稳定 ID、文档 ID、原文位置，子块带 parent_id 和前后块 ID。legacy_api.to_legacy_response() 按旧服务的字段（chunk_id、text、raw_text、metadata）输出，另外附上父块原文，服务层可以据此还原父块。

主结果

按 2,000 token 检索预算算召回率

横轴从最低值附近开始，用点而不是柱子表示，避免放大差距。

每个问题检索相似度最高的 chunk，直到累计达到 2,000 token，统计标准答案文本被覆盖了多少。按 token 预算而不是按 top-k 比，是为了不让切得更碎的实现占便宜。数值越高越好。

粒度对照

同样的 chunk 大小下谁更好

各实现切出的平均 chunk 大小不一样，而 chunk 越小，在固定预算下通常越占优。这里把 chunk_size 设为 200 / 300 / 400 各跑一遍，横轴是实际平均 token 数，纵轴是召回率。同一横坐标附近的点才是公平比较。

与旧实现对比

新实现比以前的 LlamaIndex 版本好多少

"旧版"是用以前服务的默认参数，在临时环境里运行真实的 LlamaIndex 切出的块（bench/legacy/export_llamaindex.py），再用和其他方案完全相同的 embedding 和指标评测。semantic 两边是同一个算法，只能比较参数。数值是 2,000 token 预算下的召回率，括号里是平均每块 token 数。

答案有没有被切断

做字段抽取时，一个被切成两半的值从哪一半都抽不出来。下表统计标准答案完整落在同一个块里的比例；父子块分别看子块和父块。OHR-Bench 另外单列表格类问题。旧版 layout_aware 的 100% 来自块大小没有上限（没有标题时整篇文档就是一个块），不能算优点。

显著性检验

差距是不是噪声

chunk_size 400 时，对同一批问题做配对 bootstrap（有放回抽样 5,000 次），给出"自研 − 对方"在 2,000 token 预算下召回率差值的 95% 置信区间，单位为百分点。区间不跨 0 才算显著，标为加粗。区间宽度本身也说明了多大的差距算持平：Chroma 和 OHR-Bench 约 ±2 个点，问题较少的 Qasper 约 ±3–5 个点。

Context enrichment

加上下文前后对比

LLM 为每个 chunk 写一句"这段在文档中讲什么"的上下文，拼在 chunk 前再做 embedding。因为要逐个调用 LLM，只在精简子集上跑，基线是同一子集上各方案自己的 fixed_size。

自研的基线是递归切分的 fixed_size。chroma-lite 上三个方案都跑了，结果一致，变化都在 1 个点以内。Qasper 和 OHR 子集只跑了自研，因为 context enrich 在三个方案里是同一份代码。OHR 子集只有 186 个问题、Qasper 子集只有 44 个，单个数字的波动不小。抽查发现，本地 4B 模型生成的上下文约 7% 是直接照抄原文；换成更强的生产模型后，效果预计会更好。

测试方法

数据集与口径

  • 三个方案用同一个 embedding 模型和同一个 LLM（见页首），所有 chunk 都校验了 text == 原文[start:end]，指标按字符区间重叠计算，与 Chroma 的 chunking 评测口径一致。
  • Chroma 和 OHR-Bench 在整个数据集的所有 chunk 里检索；Qasper 的问题不写论文名，所以只在对应论文内检索。
  • chonkie 的 semantic 阈值校准到与自研相近的平均 chunk 大小（0.15），其余参数都用库的默认值。LangChain 的 semantic 就是自研算法套接口，所以两行数字相同。
  • embedding 和 LLM 都用本地开源模型，换成公司的 API 后绝对数值会变，方案之间的相对差距更有参考价值。重跑方式：bench/run_bench.py --embedding-url … --llm-url …。
  • 粒度对照里，chunk_size 200 / 300 对应的 overlap 是 25 / 37 token（chunk_size 的 1/8），400 时是 50。召回率是检索指标；chunk 太小虽然检索更准，但交给 LLM 回答时上下文可能不够，chunk_size 最终要结合端到端问答效果来定。
  • 所有代码、数据下载方式和原始结果都在 document_chunking/ 目录，uv run pytest 可以跑 27 个单元测试。早期两版自研 fixed_size 的结果归档在 results/archive_v1v2/。
